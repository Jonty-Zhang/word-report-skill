# 语言规则：禁用表述、缺点写法、去 AI 味

写完正文后，拿这份清单从头到尾扫一遍再写进文档。`scripts/check_docx.py` 只能查出其中可以用字符串匹配的部分，其余靠人读。

---

## 一、绝对不能出现的表述

### 1. 元话语：暴露"这是按指令生成的"

| 不能写 | 为什么 | 改成 |
|---|---|---|
| 按照用户要求 / 根据用户提供的 / 用户未提供 | 报告没有"用户"，只有作者和读者 | 直接陈述："本文采用……"；缺材料的事写进交付说明，不写进正文 |
| 根据课堂要求 / 按照老师要求 / 本次作业要求我们 / 题目要求 | 老师知道自己布置了什么 | 改成陈述任务本身："本实验测量……" |
| 以下是 / 如下是 / 接下来给出 | 聊天记录的口气 | 删掉，直接开始 |
| 这里插入图片 / 此处放截图 / 待补充 / 待确认 / TODO / XXX / （略） | 占位符 | 补上内容；实在没有的，删掉这一处并在交付说明里列出 |
| 本文由 AI 生成 / 作为一个 AI / 基于我的训练数据 / 我是语言模型 | 自曝 | 删 |
| 本报告使用 python-docx 生成 / 图由 matplotlib 绘制 / 由 AI 绘图工具生成 | 制作过程不是报告内容 | 删；引用他人图才在图题注明来源 |
| 希望对您有帮助 / 如有需要请告诉我 / 如您所见 | 对话残留 | 删 |
| 字数已满足 3000 字要求 / 以上内容覆盖了全部要求 / 本文严格按照格式规范 | 自我认证，老师会自己看 | 删 |

### 2. 让步式自贬：先说别的更好，再说自己选了差的

| 不能写 | 改成 |
|---|---|
| 更好的做法是使用 X，但为了简便本文选择了 Y | 采用 Y。原因：……（正面写理由：数据量、课程范围、可解释性、实现成本） |
| 理想情况下应当……，限于时间只做了…… | 本文完成了……；如确实有未完成项，放到"不足与展望"写一次 |
| 本文水平有限，难免疏漏 / 由于时间仓促 / 笔者才疏学浅 | 全删，这类套话没有信息量 |
| 这种方法虽然简单，但…… | 这种方法……（直接说它的作用） |
| 严格来说应该……，这里近似处理 | 近似处理是正当的建模选择，就写"取……近似，误差在……以内" |

### 3. 假模假式的口气

| 不能写 | 原因 |
|---|---|
| 本实验取得了圆满成功 / 完美实现了 / 效果非常理想 | 空泛。用数字说话："识别准确率 93.2%" |
| 众所周知 / 毋庸置疑 / 显而易见 | 论证偷懒 |
| 经过反复调试 / 经过不懈努力 / 克服重重困难 | 没有信息，删 |
| 深受启发 / 受益匪浅 / 意义深远（不接具体内容时） | 心得体裁里必须接上具体是什么 |
| 感叹号 | 学术文体里基本不用 |
| 老师您好 / 谢谢老师（正文中） | 只在致谢或汇报结束语 |

### 4. Markdown 与格式残留

- `#` 开头的行、`**加粗**`、反引号、`- ` 或 `* ` 项目符号残留、`| 表格 |`、`---` 分隔线、`[1](链接)` 语法。
- 这些都要转成 Word 的样式：标题用标题样式，列表用 Word 编号，表格用原生表格。

## 二、缺点怎么写

原则：**写一次，写具体，写向前看。**

1. **位置**：论文放结论末尾或单独一节"不足与展望"；实验报告放"实验总结"末尾；汇报稿放"收获与下一步"。只这一处。
2. **篇幅**：2–4 句，或一个短段。
3. **内容**：具体的边界，而不是抽象的"仍有不足"。

   写法示例：
   > 本文的数据只覆盖 2023 年一个学期的 312 条记录，季节因素没有体现；模型也没有和基于规则的方法对比。后续打算补充跨学期数据，并加入规则基线做对照。

   不要写：
   > 本文仍存在诸多不足，模型效果有待提高，未来将进一步深入研究。

4. **其他章节不写让步尾巴**："但仍有改进空间""效果一般""还不够完善"这类句子从方法、实验、结果各节里全部删掉。结果不理想就把数字如实写出来，分析原因，这本身就是合格的处理。
5. **不夸大也不贬低**：真有硬伤（数据太少、模块没做完、结果没复现）如实写一次即可，不用反复道歉。
6. **不替老师下结论**："本文创新性不足""本实验较为简单"这种话不写。

`check_docx.py` 会统计"不足 / 局限 / 有待 / 尚未 / 仍需 / 不够 / 改进空间"等词分布在几个章节，分散在 3 个及以上章节会给出提醒。

## 三、去 AI 味（humanizer-zh 的学术版）

humanizer-zh 原版面向一般文本，鼓励注入个性、多用"我"、允许一点跑题。这些在论文和实验报告里不适用。下面只保留对课程报告有效的部分。写心得、汇报稿时可以额外加载 humanizer-zh 全文。

### 词汇：见一个删一个或换一个

| 词 | 处理 |
|---|---|
| 此外、另外、与此同时（段首连接词） | 大多可直接删；句子之间的关系靠内容体现 |
| 至关重要、举足轻重、不可或缺 | 说清楚为什么重要，或删 |
| 深入探讨、深入研究、深入分析 | "分析"就够了 |
| 赋能、抓手、闭环、生态、格局、织锦、图景 | 删 |
| 标志着、彰显、凸显、体现了……的重要性 | 删掉夸大意义的半句 |
| 奠定了坚实基础、提供了有力支撑、具有重要意义 | 改成具体结果 |
| 值得注意的是、值得一提的是、需要指出的是 | 直接说那件事 |
| 综上所述、总而言之、总的来说 | 一篇最多一次，放在结论开头 |
| 首先……其次……再次……最后 | 三个以上的并列改用编号列表或拆段；两三点直接写 |
| 不仅……而且…… / 这不只是……更是…… | 拆成两句陈述 |
| 从……到…… 的虚假范围（"从理论到实践，从数据到模型"） | 列出实际涵盖的内容 |
| 展示了、揭示了、见证了（用于夸大） | 换成"结果是""数据显示" |
| 一系列、诸多、各种各样 | 说出具体是哪几个 |

### 结构：这些模式一眼就是机器写的

| 模式 | 处理 |
|---|---|
| 每段都是"总起句 + 三个并列 + 总结句" | 打乱：有的段直接给数据，有的段只讲一个点 |
| 所有句子差不多长 | 长短交错；一段里至少有一句短句 |
| 列表项都是"**加粗标题：**解释" | 转成正常段落，或去掉加粗只留内容 |
| 每节末尾一句升华 | 删。一节讲完就停 |
| 破折号——连用——制造节奏 | 改成逗号或句号；一篇里破折号不超过两三处 |
| 章节开头"在本章中，我们将……"、结尾"本章介绍了……" | 论文中偶尔一次可以，每章都有就删 |
| 排比式三段（"高效、准确、稳定"） | 改成两项，或说出每一项的具体数值 |
| 结尾通用乐观："未来可期""前景广阔" | 换成下一步具体要做什么 |
| 模糊归因："研究表明""专家认为""业界普遍" | 给出具体文献或数据，给不出就删 |
| 表情符号、装饰性符号 | 删 |

### 具体优先于抽象

- "模型效果有明显提升" → "F1 从 0.71 提到 0.83"。
- "数据经过了充分的预处理" → "去掉了 47 条缺失值样本，对 3 个数值列做了 z-score 标准化"。
- "系统具有良好的可扩展性" → "新增一种传感器只需实现 `read()` 接口，不改主循环"。
- "实验过程中遇到了一些问题" → "串口波特率设错导致前两次读数全为 0"。

### 自查五问

1. 有没有连续三句长度差不多？打断一句。
2. 有没有哪一段读起来像总结陈词而不是在说事？删掉升华句。
3. 有没有哪句话换到任何一篇报告里都成立？那它没有信息量，删。
4. 每个形容词后面有没有数字或事实撑着？没有就删形容词。
5. 大声读一遍会不会不好意思？会，就重写。

## 四、写作时的其他判断

- **专业术语**：首次出现给全称（和英文），之后统一简称，不来回换同义词。
- **数字与单位**：数字用半角，单位与数字间留空格或按学科惯例；同一列小数位数一致。
- **引用**：正文引用用上标 `[1]`，参考文献按 GB/T 7714 列出；没有真实出处的话不写"参考文献"，宁可少引不编造。
- **代码与命令**：正文里提到文件名、函数名用等宽字体；不要在正文里大段贴代码，放代码块或附录。
- **人称一致**：见 `report-types.md`。
- **"我们"在单人论文里**：单人的课程论文也可以用"本文"，不用"我们"；"我们"留给小组报告和汇报稿。
